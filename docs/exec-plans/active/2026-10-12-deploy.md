# Deploy to Hetzner

## Purpose
BeanQuery runs on the owner's Hetzner VPS, next to ysto, at the owner's domain over HTTPS. Invited users reach it from any browser. The SQLite file is backed up nightly with a restore that has been tried, the collective ratings are rebuilt nightly, and the roaster registry is refreshed from every.coffee weekly. No log holds an IP address. Seen working when the owner signs in at `https://<domain>`, `/healthz` answers, and a restore drill on the VPS brings back last night's backup.

Step 10 of the [bean tracker plan](2026-10-07-bean-tracker.md).

## Context
- The owner's ysto repo is the model: a Docker image published to GHCR by a release workflow started by hand, `deploy/compose.yml` with Caddy as the only service on ports 80 and 443, a hardened Ubuntu VPS, and pull-based deploys over SSH. Its runbook is ysto's `docs/DEPLOY.md` and its reasoning is ysto's `docs/design-docs/hosting-and-deploy.md`.
- ysto's Caddy already holds ports 80 and 443 on the VPS, so both apps must share one Caddy.
- [src/web/server.ts](../../../src/web/server.ts) reads `BEANQUERY_DB`, `PORT`, `HOST`, `SECURE_COOKIES`, `DEFAULT_TIME_ZONE`, `PUBLIC_ORIGIN` and `TRUST_PROXY` ([.env.example](../../../.env.example)). The app logs no requests, only unexpected errors.
- The jobs' code exists: `rebuildCollectiveRatings` in [src/coffee/rating.ts](../../../src/coffee/rating.ts) and the live roaster fetch in [src/roaster/cli.ts](../../../src/roaster/cli.ts).
- The fonts are read from `src/web/assets/fonts/` at the package root, which tsc does not copy into `dist/`, so the image must include that folder.
- [SECURITY.md](../../SECURITY.md): dependencies and CI changes need the owner's go-ahead. The repo is public, so CI holds no credentials for the VPS.

## Plan
1. **Ops commands.** `node dist/ops/cli.js` with `backup` (an online copy through `node:sqlite`'s backup API into a dated file, then `PRAGMA integrity_check` on the copy, keeping the newest 14), `restore` (checks the backup's integrity and schema version first, keeps the replaced file aside), and `rebuild-ratings`. A `/healthz` route that runs `SELECT 1`. Tests: a backup taken during writes opens and matches, rotation keeps N, a restore round-trips, and a damaged backup is refused.
2. **The image.** A `Dockerfile` on `node:26-alpine` pinned by digest: build with pnpm, then a runtime stage with `dist/`, the production dependencies and the fonts, run as `node` under `tini`, with a `HEALTHCHECK` on `/healthz`. `.dockerignore` as an allowlist. The database lives in a volume at `/data`.
3. **The compose files.** `deploy/compose.yml`: the app with no published port, a read-only root, no capabilities and a memory limit, the `beanquery_data` volume and a backups folder on the host, on a Docker network shared with ysto's Caddy. `deploy/beanquery.caddy`: the site block for the domain. `deploy/.env.example`. The settings that must not drift (`HOST`, `BEANQUERY_DB`, `TRUST_PROXY`) are set in the compose file, as ysto does.
4. **Sharing Caddy** with ysto: a PR in the ysto repo makes its Caddy join the shared network and import site files from a folder.
5. **CI and release.** A `docker` job in CI that builds the image, runs it hardened until `/healthz` answers, checks that it holds no database or `.env`, and scans it with Trivy. A `release.yml` started by hand that publishes `ghcr.io/xms61/beanquery`. Dependabot for the Docker digest.
6. **The jobs on the VPS**: nightly backup, nightly rating rebuild and the weekly roaster fetch, each as `docker compose exec -T beanquery node dist/ops/cli.js ...` (or the roaster CLI), as systemd timers in `deploy/systemd/`, with their output in the journal.
7. **Docs.** `docs/DEPLOY.md` as the runbook (setup, release and update, the restore drill, logs and disk) and a design doc for hosting and deploy. README and ARCHITECTURE point to them.
8. **The owner deploys** by the runbook: the first start, `pnpm admin create-admin` in the container, the restore drill, and the checks below. The agent does not log in to the VPS.

## Decision log
- 2026-10-12: Take ysto's setup, on the same VPS: Docker image from GHCR, compose with Caddy, pull-based deploys by hand. Caddy gets the certificate for the owner's domain. The owner's answers in the bean tracker plan.
- 2026-10-12: The nightly backups stay on the VPS, by the owner's choice. A lost server loses them too; the JSON export each user can download is the other copy.
- 2026-10-12: Both apps share ysto's Caddy: a small PR in ysto makes its Caddy join a Docker network shared with BeanQuery and import site files from a folder, and BeanQuery ships its own site file. Each app keeps its own compose. Rejected: a separate edge Caddy (a bigger change to ysto's running setup); editing ysto's Caddyfile by hand on the VPS (the server drifts from both repos).
- 2026-10-12: CI gains a `docker` job, a hand-started `release.yml` publishing `ghcr.io/xms61/beanquery`, and Dependabot for the image digest, as in ysto, with the owner's go-ahead. Rejected: building the image on the VPS, which skips the scan.
- 2026-10-12: The jobs run as systemd timers on the host, each a command in the container, with output in the journal and missed runs caught up after a reboot. Rejected: timers inside the app, since `node:sqlite` is synchronous and a long roaster fetch would block requests.
- 2026-10-12: The VPS keeps 14 nightly backups.
- 2026-10-12: The image installs pnpm 12.10.1 with npm in its build stages only, since Node 26 ships no corepack; the runtime has neither. Docker was not running on the development machine, so CI's `docker` job is the first build of the image: it starts it hardened with a data volume and a backups folder, loads a page, the stylesheet and a font, runs `create-invite`, `rebuild-ratings` and `backup` in it, checks for database and env files, and runs Trivy. The site file names `beans.example.org`; the real domain is put in on the VPS, so the repo names none.
- 2026-10-12: A backup is written as `.partial`, passes `PRAGMA integrity_check`, and only then gets its dated name, so every `beanquery-*.db` file is a whole one; rotation counts only such files. A restore refuses a file that is damaged, is no BeanQuery database, or carries a migration newer than the code, before it changes anything, and keeps the replaced file as `<db>.replaced-<time>`. It also refuses while a `-journal`, `-wal` or `-shm` file sits beside the database, since SQLite would roll a crashed write of the old file into the restored one (found by the reviews). Every connection waits up to 5 s for a lock, so a nightly job and a user's save can overlap. It cannot tell whether the app has the file open, so the runbook stops the app first. `/healthz` runs `SELECT 1`, reads no session and is never cached; a failing database answers 503.

- On the VPS (owner): `curl -fsS https://<domain>/healthz` answers; HTTP redirects to HTTPS; the response headers carry the content policy and HSTS; `nmap` from outside shows only 22, 80 and 443; ysto still answers on its domain.
- Restore drill (owner): restore last night's backup into a scratch file in the container and open it; the account and bag counts match.
- After a night: a new backup file, and the journal shows the rating rebuild; after a week, the roaster fetch.
